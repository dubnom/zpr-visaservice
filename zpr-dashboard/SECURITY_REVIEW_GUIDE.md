# Security Review Checks

This guide documents the Control Room Security Review findings generated by `cmd/zpr-web-dashboard/static/security-review.js`. These are operator triage signals, not authorization rules: a finding does not block traffic, change a visa, or replace ZPL policy review. Visa Service and policy remain authoritative for access decisions.

## Severity

| Severity | Meaning in the review | Navigation behavior |
| --- | --- | --- |
| `high` | A repeated-denial pattern has an unknown source or sufficiently varied targets/reasons. | Raises the Security navigation indicator until acknowledged or dismissed. |
| `review` | Evidence merits operator inspection, such as a failed trusted lookup, unhealthy node, new service, or suspicious log line. | Does not raise the high-priority navigation indicator. |
| `info` | A lower-priority observation, such as an isolated denial or a newly observed actor. | Does not raise the high-priority navigation indicator. |

The table colors high findings red and review findings brown/orange; info uses the normal indicator color. Severity is prioritization only.

## Finding Rules

| Check | Trigger | Indicator and evidence shown | Severity |
| --- | --- | --- | --- |
| Isolated policy denial | A source address has denial records, but the grouped denial count is below the repeated threshold. | **Policy denial observed**. Evidence reports the grouped denied-request count and, when present, distinct destinations and deny reasons. | `info` |
| Repeated policy denials | For one source, at least **5 denial hits** or at least **3 denial records** in the current Visa Service snapshot. A record contributes `max(1, count)` hits. | **Repeated policy denials**. Evidence reports the hit count, distinct destination addresses, and distinct deny codes. | `high` if the source address is not present in the live actor inventory **or** the group spans at least **3 distinct destination/protocol/port/deny-code combinations**; otherwise `review`. |
| Trusted-source lookup failure | A trusted source in the live snapshot has `health == "failed"`. Other health values do not produce this finding. | **Trusted-source lookup failed**. Entity is the source name. Evidence uses its health note, plus the last lookup time; missing values display a fallback message. | `review` |
| Node out of sync | An actor is marked as a node, has node details, and `in_sync == false`. | **Node out of sync**. Evidence includes the reported sync state, last contact when available, and positive pending-install/revocation counts. This takes precedence over the stale-contact label. | `review` |
| Stale node contact | A node has node details and a reported last contact older than **300 seconds**. No contact timestamp by itself does not trigger this rule. | **Node contact stale**. Evidence includes the last contact and positive pending-operation counts. | `review` |
| New actor since baseline | A nonempty actor identity is absent from the saved browser-local actor baseline. | **Actor first observed since baseline**. Evidence labels it as a node or adapter/machine actor and includes its ZPR address when available. | `info` |
| New service since baseline | A nonempty service identity is absent from the saved browser-local service baseline. Identity compares service name, actor CN, kind, and endpoints. | **Service first observed since baseline**. Evidence includes kind, registering actor, and ZPR address when available. | `review` |
| Security-related adapter log | An Adapter Logs line contains one of the case-insensitive phrases listed below. | **Security-related log message**. Entity identifies adapter and source; evidence is the matching line, truncated to 600 characters. | `review` |
| Aggregate DNS probing | While Security Review is open, two or more BIND counter samples show, within the last 60 seconds, at least **30 DNS requests**, at least **20 NXDOMAIN responses**, and NXDOMAIN is at least **60%** of requests. Counter decreases reset the sampling window. | **DNS probing pattern (aggregate)** for **DNS service**. Evidence reports NXDOMAIN count, request count, and elapsed window. It explicitly notes that aggregate counters cannot identify the source. | `review` |

The suspicious-log phrases are matched as whole words, case-insensitively:

- `authentication failed`
- `failed authentication`
- `auth failure` or `authentication failure`
- `login failed`
- `invalid certificate`
- `certificate verify failed`
- `unauthorized`
- `access denied`
- `permission denied`
- `invalid token`

Log text is treated as evidence, not proof: only configured Adapter Logs sources are scanned, and a source/API failure can leave this check without data.

## Tuning

The thresholds and detection phrases are currently hard-coded in `cmd/zpr-web-dashboard/static/security-review.js`; there is no operator settings file or UI for them yet.

- Denial repetition: change `group.hits >= 5` and `group.records.length >= 3` in `denialFindings`.
- High denial classification: change the unknown-source check against live actor ZPR addresses and/or the `varied` threshold of 3 distinct destination/protocol/port/reason tuples.
- Node freshness: change the `contactAge > 300` seconds test in `nodeHealthFindings`.
- Log phrases: edit `suspiciousLogLine`. Keep the word boundaries and case-insensitive flag unless substring matches are intended; broad terms can create noisy findings.
- DNS probing: change the 60-second sample window and the `30` request, `20` NXDOMAIN, and `0.6` ratio thresholds in `dnsProbeFindings`. The counters are service-wide, so this remains an unattributed `review` finding; it is deliberately excluded from the high-priority navigation indicator.
- Finding volume: the combined, severity-sorted list is capped at 250 entries in `scan`.

After changing a rule, update its browser regression in `tests/browser/dashboard.spec.mjs` and verify both the generated indicator and its severity/navigation behavior. The signal sources are the Control Room snapshot (`recent_denies`, `trusted_sources`, actors, and services), `GET /api/adapter-logs`, and BIND counters at `GET /api/dns/stats/json/v1/server`. DNS probing is sampled on Security Review refreshes, not continuously in the background; short bursts between samples can be missed.

## Baseline and Alert State

- The first successful scan while Security is open creates a baseline from current actor names and service identities if none exists. Reset Baseline replaces that comparison point; it does not clear dismissals.
- Baseline and dismissal records are stored in this browser's local storage. Dismissals are keyed by indicator, entity, and evidence, and persist across reloads in that browser.
- Visiting Security acknowledges currently observed high navigation alerts but does not dismiss their findings. The acknowledgment is in page memory; a new high finding, changed evidence, newer denial timestamp, or a resolved alert that recurs can raise the indicator again.
- A disconnected or incomplete source is not evidence that the system is healthy. Check the source error and refresh before interpreting an empty finding list.
