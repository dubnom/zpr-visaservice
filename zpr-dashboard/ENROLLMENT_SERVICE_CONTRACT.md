# Enrollment Service API Contract

**Status:** proposed version-1 production contract; not implemented or deployed.
The current administration handlers run in Control-Service and use the current
SQLite invitation store. The standalone device listener implements only the
challenge/proof claim and status flow. Do not infer production inventory,
credential issuance, admission, renewal, revocation, or retirement from this
document or those prototypes.

The current device-flow prototype binds a separate BAS runtime RSA public key
and fingerprint alongside the enrollment proof key. Claim and status proofs
must be signed by both private keys, and operator review/cancellation binds
both displayed fingerprints and the invitation revision. This does not issue a
BAS credential or implement the approved, one-time Keychain-to-root handoff.

## Service boundary

The Enrollment Service is the sole writer and authority for pre-enrollment
assets, invitations, requests, issued device identities, and their lifecycle.
It owns its durable store. Control-Service calls its administrative API over
the control network using mutually authenticated TLS and an independently
configured client identity; it must not open the Enrollment Service database.
Control-Service forwards a verifiable, short-lived named-user delegation
containing the operator issuer and subject. The Enrollment Service validates
the delegation, scopes it to this service, organization, operation, body and
request, and consumes its replay nonce durably.

Devices use a separate HTTPS listener reachable only over the private
corporate underlay or VPN before ZPR admission. It exposes no administrative
routes. TLS is end-to-end; TLS termination is unsupported. Neither service
trusts caller-supplied identity, organization, client-IP, or forwarded headers.
The Enrollment Service and Control-Service remain independent of Simulator.

## Common contract

- Base path is `/v1`. Administrative and device listeners have distinct
  authorities, credentials, route allowlists, and rate limits.
- JSON requests and responses use UTF-8, reject unknown fields, trailing data,
  invalid values and oversized bodies, and never include private keys,
  enrollment codes after creation, or credential secrets in URLs or logs.
- Administrative routes require an authenticated named-user delegation and
  service-side permission and organization checks. Device routes require
  server-authenticated TLS, a locally generated key, and a valid proof of
  possession. Possession of an invitation code alone never authenticates a
  claimed request or retrieves credentials.
- Every mutation uses an `Idempotency-Key` with a bounded lifetime and stores
  its operation, caller, organization, request digest, and non-secret result atomically
  with the state transition and audit event. Reuse with a different digest
  returns `409`. A lost response may be reconciled by a read; clients do not
  blindly retry uncertain mutations.
- State-changing review calls include `expected_revision` and bind the
  organization, resource ID, and key fingerprint where applicable. A stale
  revision, changed key, expired deadline, or competing transition returns
  `409`; the caller must fetch fresh details before deciding again.
- For example, asset creation accepts
  `{"organization":"...","asset_id":"...","name":"...","owner":"...",
  "type":"...","profile":"..."}`; invitation creation accepts
  `{"organization":"...","asset_id":"...","expected_asset_revision":4}`.
  The one-time code is generated by the service and appears only in the
  successful invitation-creation response. The service chooses invitation
  expiry from its explicit configured lifetime; callers cannot extend it.
  Review bodies include `expected_revision`, `expected_asset_revision`,
  `key_fingerprint`, and a required bounded `reason`.
- All state transitions, permission checks, idempotency consumption, credential
  issuance records, and audit writes that form one operation commit atomically.
  Audit records include authenticated principal, action, organization, target,
  request/revision identifiers, result, and time; they exclude codes, private
  keys, tokens, and credential material.
- Unauthenticated/unauthorized callers receive `401`/`403`; malformed bounded
  requests receive `400`/`413`; missing scoped resources receive `404`;
  conflicts and expired/stale preconditions receive `409`; rate limits receive
  `429` with `Retry-After`; unavailable dependencies fail explicitly with
  `503`. Error bodies use `{"error":{"code":"...","message":"..."}}` and do
  not reveal whether another organization's resource exists.
- Limits, lifetimes, issuer trust, and cryptographic algorithms are explicit
  operator configuration. No missing setting silently selects a production
  default. Capacity enforcement must work across service instances, not only
  in process memory.

## Administrative API

Administrative permissions are organization-scoped: `read`, `inventory_write`,
`create`, `cancel`, `approve`, `reject`, `revoke`, and `retire`. Capability
catalogs expose only the organizations and operations authorized for the
current named user. Creation and review authorization is checked again by the
Enrollment Service on every mutation, not inferred from a GUI control.

| Method and path | Permission | Contract |
|---|---|---|
| `GET /v1/catalog` | `read` | Return authorized organizations, approved device types/profiles, supported package metadata, allowed operations, and configured lifetime bounds. No secrets. |
| `GET /v1/assets?organization=&cursor=&limit=` | `read` | Paginated inventory; every item has organization, immutable asset ID, state, revision, approved profile/type, and non-secret display metadata. |
| `POST /v1/assets` | `inventory_write` | Create a `pending` asset from an asset tag and optional display name plus approved owner/type/profile. Returns the committed asset, revision, and audit ID. |
| `GET /v1/assets/{asset_id}?organization=` | `read` | Return one organization-scoped asset and current revision. |
| `PATCH /v1/assets/{asset_id}` | `inventory_write` | Update allowed inventory fields only with `expected_revision`; device claims cannot call this route. |
| `POST /v1/assets/{asset_id}/retire` | `retire` | Retire an asset with expected revision and reason. An active identity must be revoked before retirement completes. |
| `GET /v1/invitations?organization=&cursor=&limit=` | `read` | Paginated invitation summaries; never returns enrollment codes or credential material. |
| `POST /v1/invitations` | `create` | Create an invitation for an active or pending asset using its current inventory revision. Enforce one active invitation per asset. The response includes the one-time enrollment code exactly once; persist only a verifier. |
| `GET /v1/invitations/{id}?organization=` | `read` | Return fresh details, including asset and invitation revisions, state, creator, deadlines, both claimed key fingerprints, and decision audit fields. No code. |
| `POST /v1/invitations/{id}/cancel` | `cancel` | Cancel an invited or pending request with expected revision, enrollment and BAS runtime key fingerprints, and reason. An approved identity requires revocation, not invitation cancellation. |
| `POST /v1/invitations/{id}/approve` | `approve` | Approve a key-bound pending request with expected invitation and asset revisions, exact enrollment and BAS runtime key fingerprints, and reason. Activate a pending asset and bind both keys atomically. Approval authorizes issuance, not successful delivery or network admission. |
| `POST /v1/invitations/{id}/reject` | `reject` | Reject a key-bound pending request with the same revision and both key bindings and a reason. Rejection is terminal for that request. |
| `GET /v1/devices?organization=&cursor=&limit=` | `read` | List issued identities and separate lifecycle/connectivity metadata. Connectivity is observed from production Visa Service contracts, never Simulator. |
| `GET /v1/devices/{device_id}?organization=` | `read` | Return identity state, asset/profile, key fingerprint, credential expiry, issuance/revocation status, and source timestamps; never return credential secrets. |
| `POST /v1/devices/{device_id}/revoke` | `revoke` | Revoke the identity with expected revision, key fingerprint, and reason. Return a propagation operation/status ID; do not report complete until trusted identity and Visa Service enforcement confirm it. |
| `POST /v1/devices/{device_id}/retire` | `retire` | Retire a revoked identity with expected revision and reason. Preserve audit history and reject future renewal/admission. |

Successful mutation responses include the committed resource, resulting
revision, audit event ID, and any asynchronous operation ID. The approve
response also returns the durable `issuance_operation_id` used for result
delivery. The create invitation response additionally contains
`enrollment_code` once. The service never persists the code or a response
containing it: replaying that idempotency key returns the non-secret committed
invitation summary and marks the secret unavailable. If the code response was
lost, cancel and replace the invitation; never recover or resend its code.

Asset IDs are immutable and unique within an organization. Asset state is
`pending`, `active`, or `retired`; invitation state is `invited`,
`pending_approval`, `approved`, `rejected`, `cancelled`, `expired`, or
`approval_expired`; device identity lifecycle is `issued`, `revocation_pending`,
`revoked`, or `retired`. Connectivity is separately `connecting`, `connected`,
`disconnected`, or `unknown/stale`, with an observation timestamp and source.
Do not derive one lifecycle from another. In particular, `approved` is not
`issued`, and `issued` is not `connected`.

Invitation, approval, and credential lifetimes are independently configured,
positive, bounded, and visible in the relevant response. Expiry of one does
not imply expiry of another. Approval requires a current invitation and asset
revision, an authorized human decision, the exact claimed key, and any
profile-required evidence. In the initial single-operator configuration, the
creator may approve their own invitation; this exception must be explicitly
configured and audited. Before multi-operator production use, creator
self-approval is a deferred security issue: enforce distinct issuer/subject
for creator and approver in this service's transaction and test it. See the
[security hardening tracker](./SECURITY_HARDENING.md#p1-enrollment-approval-separation-of-duties).

## Device API

The device client generates and retains its private key locally. A signed
challenge binds protocol version, service audience, purpose, organization,
invitation ID, key fingerprint, nonce, and expiry. Challenges and replay
consumption are durable, bounded, and single-use.

| Method and path | Purpose | Contract |
|---|---|---|
| `POST /v1/challenges` | Claim | Submit `{"purpose":"claim","organization":"...","invitation_id":"...","enrollment_code":"...","public_key":"<base64 DER SubjectPublicKeyInfo>","runtime_public_key":"<base64 DER SubjectPublicKeyInfo>"}`. Return a short-lived challenge only if the invitation is active and the code verifies. Do not consume the invitation merely on challenge creation. |
| `POST /v1/proofs` | Claim | Submit `{"challenge_id":"...","signature":"<base64 enrollment signature>","runtime_signature":"<base64 BAS runtime signature>"}` over the exact challenge payload. Atomically consume challenge, claim invitation for both keys, create pending request, set approval deadline, and audit. Repeating a consumed proof cannot create a second request. |
| `POST /v1/challenges` | Status | Submit `{"purpose":"status","organization":"...","invitation_id":"...","public_key":"...","runtime_public_key":"..."}` for the already-bound keys; no invitation code is accepted after claim. |
| `POST /v1/proofs` | Status | Verify possession of both private keys and consume the challenge. Return only the authorized request/identity state and operation status, never admin-only inventory fields or secrets. |
| `POST /v1/challenges` | Issuance result | Submit `{"purpose":"result","organization":"...","invitation_id":"...","public_key":"..."}` for the bound key after approval. |
| `POST /v1/issuance/{operation_id}/result` | Result delivery | Submit the fresh `challenge_id` and signature for the `result` purpose. Return the same idempotent issuance result. It contains an issuer-signed, versioned device credential/configuration bound to organization, asset, identity, and public key, but never the private key. |
| `POST /v1/challenges` | Renewal | Submit `{"purpose":"renew","organization":"...","device_id":"...","credential_revision":N,"public_key":"..."}` for the current, active identity. Reject revoked or retired identities. |
| `POST /v1/credentials/renew` | Renewal | Submit the challenge ID and signature for the `renew` purpose. Recheck inventory, profile, revocation, issuer validity, and current credential revision atomically. Return the replacement credential once; retries reconcile the same issuance result. |

The challenge payload is the exact UTF-8 JSON byte sequence signed by both
device keys. It contains protocol version, audience, challenge ID, purpose,
organization, invitation or device ID, both key fingerprints, random nonce, and
expiry. The service validates the audience and all caller context before
creating it. The device verifies those fields against its trusted endpoint,
local keys and saved request before signing. Challenge creation does not
consume the invitation; only one successful proof from both keys consumes a
challenge and performs its bound transition.

The exact credential format and key type must be selected with the Visa
Service/adapter integration before issuance is implemented. Enrollment proof
keys are not presumed to be the adapter Noise/link key. The issuer must bind
credentials to the approved public key and identity and publish only the
trusted attributes mapped from the approved, versioned profile. No credential
is issued before approval. A lost delivery response must resume the same
issuance operation; it must not create another device identity or mint a
second independent credential.

## Revocation, admission, and failure behavior

Revocation is a durable state transition followed by enforcement at the
trusted attribute/identity provider and Visa Service. The API reports
`revocation_pending` until both deny new authentication and terminate or remove
existing admissions/visas. Failed or unavailable enforcement remains pending
or explicitly failed and triggers operator-visible retry/reconciliation; a
registry flag alone is not success. Renewal and reconnect fail closed as soon
as revocation begins. Retirement requires confirmed revocation.

The service must not issue a ZPR address, assert a successful connection, alter
policy, or add a per-device static bootstrap entry. Visa Service remains the
authority for observed node/admission/connectivity data; Policy-Service remains
the authority for policy. If either source is unavailable or stale, report
unknown/unavailable rather than successful admission.

## Migration and acceptance

This contract intentionally separates production ownership from the current
prototype routes `/api/enrollment/v1/` and `/enrollment/v1/`. The prototype's
admin handler is mounted in Control-Service and its device listener persists
in the enrollment SQLite registry; neither is the production Enrollment
Service described here. Implement a separately hosted service and client,
versioned durable inventory and identity schema, transactional/idempotent
operations, issuer/provider integration, and private-network deployment before
marking this contract production-ready.

Acceptance requires contract tests for organization and permission isolation,
forged identity and forwarding headers, idempotency conflicts, replay after
restart, duplicate assets, stale inventory/invitation/key revisions,
concurrent claim/decision/issuance/revocation, code secrecy, bounded body and
rate limits, dependency outages, approval-to-delivery failures, renewal,
revocation propagation, and retirement. Run with Simulator stopped, its
environment variables unset or invalid, and no Simulator APIs available.
