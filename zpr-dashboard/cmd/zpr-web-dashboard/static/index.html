Checking enrollment administration…

            

            
Invitation creation requires explicit backend opt-in and named-user create grants. Authorized admins can cancel invited or pending requests, or approve/reject pending key proofs, from fresh Details using the current revision and exact fingerprint. Verify the fingerprint through an independent trusted channel; every decision needs a reason and independent backend authorization. Review approval does not issue credentials or establish connectivity. Enrollment APIs require configured HTTPS sign-in and independently verified named-user delegation to Control-Service. The shared service certificate alone is not administrator authority. Direct certificate-authorized administration remains separate.

Enrollment workflow

                
    
                  
  1. Invite
    An authorized administrator validates inventory and approved catalogs, then creates an expiring, single-use invitation. The machine need not be present or online.
    2. 
                  
  2. Deliver separately
    Send instructions and the generic installer link. Deliver the code through a separate authenticated secure channel. Automatic email delivery is not implemented.
    3. 
                  
  3. Run on the new machine
    Verify the versioned manifest and detached signature using independently trusted signing information before installing. Run the local setup wizard as the desktop user; the machine needs enrollment-service connectivity.
    4. 
                  
  4. Review key proof
    Compare the machine's key fingerprint through a trusted channel. Approval is bound to the current revision and verified key, with a recorded reason and an approval deadline.
    5. 
                  
  5. Issue and admit separately
    Approval does not issue credentials or prove live ZPR connectivity. Credential issuance and adapter admission are not implemented.
